# PR #3078 唤醒词扩展实施记录

日期：2026-09-11。基线：`40b1ca8a7a9266119f4521a9468b8dff11e607d8`。
实施分支：`codex/voice-wake-word`。本记录区分代码验证与识别效果验收。

## 实现行为

已录入并启用语音激活、输入和两种模型准备成功时，关键词命中可以独立
激活。普通语音仍使用原有声纹阈值 0.40 和 1.5 / 3 秒检查点。配置与
模型安装见 [本地唤醒词说明](voice-wake-word.md)。未配置模型时保留原行为。

- 中立契约携带完整 generation、待机 epoch 和原 PCM 采样范围；通用
  控制器不包含具体名字，也不把关键词证据伪装成 OWNER。
- 运行时把接纳后的连续 16 kHz PCM（含静音）交给有界队列与隔离推理
  进程。推理不占状态机锁；队列溢出、准备或运行失败进入不可用状态。
- 控制器在锁内检查状态、轮次、缓存范围及有效期。关键词活动时间通过
  原帧时间轴映射，迟到结果不会凭推理完成时间续期。
- 两种成功来源共用回放提交和单写者。唤醒起点保留约 300 ms 前导，
  后续缓存接续；Core 为两种来源递增首句交付批次，native 与独立 ASR
  继续使用同一输出入口和原有回执规则。
- 关键词提交撤销旧评分请求权限，不盲目取消评分器；旧任务返回及
  finally 只操作自己持有的身份，最多保留一个当前待处理请求。
- 回待机建立新检测轮次；有效人声连续约 30 秒未更新时按原计时机制
  回到 WAITING。ACTIVE 不等于 Provider 已确认或已产生回复。
- 设置帮助文案同步八种语言，并更新 locale 缓存版本。

## 长待机时间戳问题（2026-09-11 现场排查）

Electron 真人测试报告“没反应”后，离线复现出确定的阻断：在正例前输入
12 秒静音，原版 1.13.8 在第 12.96 秒命中，但报告名字起点约第 1.04 秒。
该位置已被 8 秒缓存淘汰，控制器正确拒绝回放。此前短样本通过不能覆盖此场景。

根因在底层 `KeywordSpotterTransducerImpl::Reset`：静音触发重置会清空
解码器 `frame_offset`，而原输入流继续累积。C API 的 `start_time` 仍为零，
Python 接口也未暴露它，简单相加无法修复。原始用户失败可能还包含识别漏检，
不能仅凭这个离线反例断言每一次真人失败都由此造成。

当时仓库保留最小上游源码补丁和 Windows wheel 构建脚本，修复版标识为
`1.13.8+neko.kws1`。它保留重置前的累计帧偏移，继续清空声学状态和解码假设。
后端拒绝未验证运行库版本，避免依赖重新安装后静默回到错误映射。
新增真实模型用例覆盖静音 12 / 45 秒后唤醒、缓存淘汰后的有效音频范围、
一次回放和原 PCM 顺序。

当时的 kws1 Windows cp311 wheel 已构建；SHA256 为
`cc8d9456f6cf7945e74fb3b789bb866fb78e9926103b9efc5338f4a60b9ff9ea`。
原版反例与修正版使用相同合成音频；12 秒静音后，名字起点由错误的
1.04 秒恢复到约 12.24 秒，45 秒静音后约为 45.28 秒。连续流显式重置后
第二次命中的独立探针也通过。针对后端、控制器、运行时和 Core 的
82 项回归通过，后端模块覆盖率 92.39%，未重跑仓库全量测试。

14:09 已用该 wheel 重启 main / memory / agent，三项健康检查同属新实例
且均为 ok。此记录证明本地部署和合成音频回归，不代表真人识别率验收。
