## 1. 产品依据与已经确认的规则

以 Wehos 在 2026-09-08 的两段对话为准：声纹用于激活；待机可以无差别缓存音频，激活时回放；短音频可以不能激活，但激活状态下不再按声纹拦截；激活保持一段时间；能力覆盖独立 ASR 和原生音频对话。优先解决语音会话闲置激活，实际分发、性能和系统环境是首版验证重点。

用户已经确认：**连续 30 秒无人说话后回到待机**。不是激活后固定 30 秒强行结束，也不另加未经确认的连续对话最长时限。

本方案中的“声纹档案启用／模型就绪”与“语音对话已激活”必须分开命名和呈现，避免复用旧代码的 activation 一词后混淆配置状态与对话状态。

| 场景 | 必须表现 |
|---|---|
| 麦克风开启，声纹激活功能开启 | 本地收音、有限缓存，等待本人语音 |
| 待机时只说很短的“嗯／好” | 可以无法激活；不拼接下一句、不补静音制造验证时长 |
| 获得有效本人证据 | 激活，回放本次候选开头，再接续实时输入 |
| 已激活，本人说短句 | 不再因为声纹证据不足拦截，继续走正常语音链路 |
| 已激活，旁人说话 | 同样可能进入对话，属于该模式的产品取舍 |
| 连续 30 秒无人说话 | 回到本地待机，下一次对话重新需要激活 |
| 显式关闭声纹激活功能 | 进入普通语音模式；界面明确不再要求声纹激活 |
| 关闭麦克风／结束语音会话 | 停止采集，撤销权限，清空本地缓存并回收工作任务 |

声纹不是唤醒词识别，也不能判断“本人是不是在对猫娘讲话”。不要求口令的前提下，本人对其他人说话也可能激活。声纹不是活体认证；本轮不扩展抗录音重放能力。

## 2. 首版范围与排除项

### 2.1 首版必须完成

1. 通用音频入口的待机／验证／激活／闲置恢复控制。
2. 有界缓存与首次激活音频回放，保证顺序和发送失败语义。
3. 复用 CAM++，评分不依赖 ASR 的文字、utterance ID 或远端起止事件。
4. 独立 ASR 和原生音频两条生产组装路径均接入。
5. 激活模式停用旧的逐句声纹拒绝器。
6. 配置、运行状态、错误和关闭流程在 Web／Electron 一致。
7. 可分发的模型资产与运行依赖验证，普通 CPU 的资源测试和实际发行环境检查。
8. 录入音频与实时评分采用一致的处理合同；必要的录入修复不能省略。

### 2.2 本轮不引入

- pVAD、ECAPA、ECAPA2、TSE 或短句校准参数包。
- 每句重新识别身份、连续多人声纹分段、重叠声源提取。
- #2980 的 exact 子回合提升、混合证据粘滞拒绝、拒绝后静音重武装等整套增量。
- 更换 ASR Provider、改动 Core→ASR 的选择规则。
- 把语音激活用作文字输入、游戏命令、图片输入的全局权限系统。
- 未验证平台的“全平台已支持”承诺，或为绕过安全存储限制改用明文档案。

“先上线接受考验”解释为先交付这套范围有限且可回退的能力，实测后继续迭代；不解释为可以跳过录音错投、重复发送和模型无法分发等基本检查。

## 3. 基线与 #2980 复用清单

main 已包含 CAM++、基础档案加密、单段录入服务、统一音频处理、独立 ASR/native 共同分流入口，以及旧版逐句过滤。因此新方案不需要搬入 #2980 的整个语音运行时。

| 模块／能力 | 复用方式 | 依赖边界 |
|---|---|---|
| CAM++ 权重、manifest、特征前端和基础推理 | 优先使用 main | 不带入短输入探测作为激活依据 |
| 声纹档案、安全存储、配置读写 | 在 main 上扩展 | 保留校验和原子保存；明确音频合同版本 |
| 3×3 秒参考＋1×5 秒验证、2 秒准备 | 从 #2980 提取完整功能补丁 | 连同后端 API、前端状态、8 语言和必要测试；不迁辅助模型卡片 |
| 录入与运行时归一化、EOF 尾部结算 | 提取必要修复 | 与取消、异常清理配套；不改变普通实时流的 EOF 语义 |
| 评分进程、串行调度、关闭回收 | 复用已验证机制，做轻量适配 | 不直接复制最新版共享宿主，因为它依赖 pVAD 和扩展 Shadow runtime |
| 会话／档案代次、迟到回调防护 | 复用设计与相关修复 | 为激活状态定义自己的代次，不引入 exact 证据协议 |
| 缓存与发送器 | 复用有界容器和单写者思路 | 现有 700 ms ASR pre-roll 不足以承担激活回放，不能仅调大常量冒充完成 |
| 原逐句声纹过滤 | 本模式不挂载 | main 已有的过滤也必须处理，不能只是不搬 #2980 增量 |

提取方法：先比较功能引入前后的差异，再检查后续修复，制作针对 main 的最小补丁。早期提交只作来源，不能默认它没有后续修复过的缺陷。每个提取补丁都要说明来源、保留行为、丢弃依赖和回归用例。

## 4. 总体架构和依赖方向

```text
麦克风输入与采集身份
  → 统一降噪／AGC／limiter／16 kHz 单声道 PCM
  → 通用语音激活控制
       ├ 待机：本地活动检测＋有限缓存＋CAM++ 候选评分
       └ 激活：有序回放／实时转发，停止身份检查
  → 既有音频路由
       ├ 独立 ASR → 原有断句与文本交付 → Core
       └ 原生音频会话 → Core
```

建议分为三层：

- `main_logic/voice_input/activation/`：配置、状态机、帧缓存、权限代次和输出决策。只依赖中立帧与评分接口，不 import Core、Provider 或应用组装模块。
- `main_logic/voice_identity_service/`：CAM++ 评分适配、档案兼容和资源所有者；模型失败返回明确状态，不替激活控制器决定自动放行。
- `main_logic/core/asr_runtime.py` 与 `app/main_server/voice_identity_runtime.py`：组装、接线、配置同步和生命周期。Core 不承载声纹策略算法。

评分接口只接收 PCM、采样率、档案／模型代次和候选身份，返回有效分数或分类失败；不接收 transcript、ASR utterance 或 Provider exact proof。

本地活动检测负责候选起音和闲置时间；远端 VAD／SmartTurn 保留自己的断句职责。两者可以各有独立流状态，不共享会被不同调用者 reset 的同一个可变实例。

## 5. 状态机与闲置规则

| 状态 | 音频处理 | 退出条件 |
|---|---|---|
| DISABLED | 普通语音路径，不缓存待激活音频 | 用户启用功能 |
| PREPARING | 本地有界缓存；尚无对话授权 | 模型和档案可用，或准备失败 |
| WAITING | 本地活动检测与缓存，未向对话 Provider 发送麦克风 PCM | 候选达到评分条件 |
| VERIFYING | 推理在后台进行，采集继续，缓存有界 | 本人证据成立／不成立／失败／失效 |
| REPLAYING | 唯一发送者先排空选定缓存，再衔接实时输入 | 队列追平，或发送失败 |
| ACTIVE | 正常转发；不进行逐句声纹过滤 | 连续 30 秒无人说话／权限撤销 |
| UNAVAILABLE | 显示原因；功能开启时不自动放行待机音频 | 用户重试、修复条件或显式关闭功能 |
| CLOSED | 不采集、不发送、清除本代缓存和任务 | 新建麦克风会话 |

### 5.1 30 秒规则

- 基于本地有效人声活动和单调时钟计时，不基于 ASR final 到达时间。
- 激活期间的任意有效人声都可以更新闲置时间；因为此时不再验身份，不能宣称“只有本人可以续期”。
- 新的人声在 30 秒截止前实际采集到，允许续期；截止之后开始的声音需要重新激活。按采集顺序处理截止附近的帧，不按后台任务完成顺序猜测。
- 回放旧缓存不能把它当成新的人声反复续期。帧保留原始采集时间与序号。
- 不能因为每帧都有 PCM／背景噪声，或者 TTS 正在播放，就自动续期。
- 自身播放回声被麦克风误识别为人声的风险必须实测；仅靠播放状态不能证明回声已消除，也不能简单在 TTS 期间禁麦导致无法插话。
- 到期只影响之后的新输入；已发送且仍在等待 final／回复的旧回合按原合同完成，不删除历史，不重投音频。
- 不引入额外的固定最长激活时间。持续有人讲话时可以持续 ACTIVE，但资源必须保持有界。

### 5.2 与 Provider 会话的关系

待机不是关麦，也不要求所有 Provider WebSocket 永久保持连接。可复用现有连接预热能力；连接已超时就按原协议重建，在准备完成前继续有界缓存并显示状态。

不得用假人声或循环静音保活规避 Provider 的空闲限制。也不承诺待机无连接费或零远端成本；本方案只约束待机麦克风 PCM 不进入对话 Provider。

## 6. 缓存、回放与发送约束

### 6.1 缓存范围

无差别缓存指采集时不先按说话人丢帧；不等于激活后把全部历史缓存上传。回放选取当前候选语句及有限前导上下文，避免补送几秒前另一人的完整发言。

此处候选由活动与停顿界定，不是已经实现说话人分离。同一连续候选内先旁人后本人、或两人重叠，回放仍可能包含旁人；首版明确保留这一限制，不伪造逐帧 Owner 证明。

建议初始工程参数如下，均是待测参数，不是已验收结果：

| 参数 | 初始建议 | 说明 |
|---|---|---|
| 环形音频缓存 | 8 秒／256,000 字节 PCM16 | 16 kHz 单声道；另计帧元数据和评分快照 |
| 候选前导上下文 | 约 300 ms | 通过首字完整性实测调整 |
| 候选评分时间 | 优先复用 1.5 秒和 3 秒长输入条件 | 满足语音质量条件；不以静音凑长度 |
| 同时在途评分 | 1 个 | 不因每帧到达创建推理任务 |
| 等待评分队列 | 至多 1 个候选 | 旧候选失效／结束后有序接续，不无限积压 |
| 单候选缓存覆盖 | 必须完整处于缓存内 | 开头被淘汰后不拿不完整片段冒充完整激活语句 |

最终缓存、候选和评分字节数同时设硬上限；候选快照数量不随会话长度增长。

### 6.2 回放必须满足

1. 每帧绑定采集序号、采样范围、采集时刻、路由／会话／麦克风代次。
2. 激活时固定回放截止序号；此后新帧排在回放之后，由同一个发送者处理。
3. 不重新做一次降噪或重采样；使用已经归一化的缓存帧，保留来源身份。
4. 每帧至多交给下游一次；回放不能再进入自己的待机缓存或再次触发激活。
5. 新模块与既有 ASR pre-roll／hot-swap 缓存分别记录“已提交”范围，禁止重复补头。
6. Provider 能否加速接收积压音频、最大帧尺寸、接续延迟必须按实际适配器验证。不得默认所有实时接口支持瞬时灌入数秒音频。
7. 回放无法追平、队列溢出或时间线断裂时，停止本次交付并显式失败，不能悄悄丢中间帧。

### 6.3 部分发送失败

严格区分未发送、已写 transport、Provider 已确认、已进入历史。只有能证明未发送的帧才允许继续原操作。已写入或发送结果不明时不自动整体重放；必要时按适配器合同结束不安全会话，提示重试。

关闭功能时丢弃待机缓存，不能因用户取消声纹功能突然补送之前一直未授权上传的录音。

## 7. 评分、档案和失败语义

- 首版继续使用 CAM++，不通过更换模型解决激活状态机问题。
- 1.5 秒是现有标准输入的工程起点，不是身份可靠性的数学界线。短句不能激活是允许的；长句也可能误拒或误激活，需要分别记录。
- 旧 `0.40` 只可作为初始试验阈值。旧系统的“两次低分拒绝、其余放行”不能直接改名为“本人确认”；新策略需要明确的正向激活条件，并验证整个待机会话的误激活率。
- 初版可在有限的 1.5／3 秒候选上评估明确正向分数，不无限滑窗反复抽奖。最终阈值与重试步长在开发样本上冻结，再用独立录音验收。
- 待机遇到短句、不足、低分、NaN、档案错配、超时或模型失败均不激活；失败原因与普通“尚未确认本人”分开显示。
- ACTIVE 时不再运行身份评分。评分器发生故障不应凭空追溯拒绝已经激活的语音；到期重新激活时才要求评分能力恢复。输入／传输故障仍由既有语音链路处理。
- 档案被删除、替换、显式禁用或麦克风权限撤销时立即撤销对应激活权限；不能把旧档案的授权留给新档案。
- 复用 3+1 录入时，音频处理、特征模型、参考形成方式和档案版本一并绑定。兼容性无法证明的旧档案提示重新录入，不直接把不同处理域的向量混用。
- #2980 的辅助参考和新版档案不能无条件移入 main；首版只声明经过检查的 CAM++ 档案兼容范围。实验分支测试使用隔离状态目录，避免把用户正在使用的档案重写为另一套 schema。

## 8. 生命周期、并发和资源所有权

评分／回放任务捕获麦克风代次、输入所有者、路由／会话代次、档案／模型代次、候选编号和权限修订号。任何 await 后，在激活、发送、发布状态或清理前重新检查。

| 事件 | 必须动作 |
|---|---|
| 关闭麦克风／结束会话 | 先封住新产出，再取消与回收；清空缓存和权限 |
| 路由切换／重连 | 旧回放不转投新会话，旧评分不授权新路由；首版保守重新激活 |
| 开始录入／更换档案 | 撤销旧权限，等待旧评分退出，新档案成功后重新待机 |
| 切换输入所有者 | 防止聊天缓存进入游戏或另一角色；未支持路径显示明确状态 |
| 取消／推理超时 | 回收底层进程或保留被隔离的退休所有者，不能只取消等待 |
| 旧任务迟到 | 只清理自己持有的资源，不能关闭接管者或发布 ACTIVE |
| 关闭后重开 | 新代次、新权限；不使用上次缓存和验证结果 |

资源方案优先复用已有的可终止工作进程机制。一个实际采集入口只保持一个评分工作者；禁止每次尝试激活启动一个新进程、禁止 Web 与 Electron 同时重复评分同一输入。

模型加载、推理、文件校验与关闭不在音频事件循环中同步执行。评分队列单飞；关闭不能因底层永久阻塞而不断创建后继进程。模块所有者明确负责进程、管道、数组、定时器和回调的最终回收。

## 9. UI、配置和隐私

设置名称建议“声纹激活语音对话”，说明：“确认是你后开始对话；对话期间可直接接话，连续 30 秒无人说话后重新等待激活。”另说明“激活期间也会接收附近其他人的声音”。

运行状态至少区分：功能关闭、准备中、等待你说话、已激活、暂时不可用。不能把“模型已安装”显示为“对话已激活”。录入页面继续显示档案状态；会话状态通过带代次的事件更新，不用高频全局刷新。

声纹功能偏好与运行时 ACTIVE 状态分开存储；ACTIVE 不跨进程重启、角色切换或麦克风会话持久化。30 秒暂作默认内部配置，首版不必增加复杂调参界面。

提取四段录入时，浏览器和 Electron 均保留准备、录制、验证、取消、关闭页面释放等状态。所有新增文案同步 8 个 locale。

缓存只在本地有界内存；不把原始 PCM、embedding、完整转写和实际声纹分数写入持久日志。允许记录匿名原因、耗时、缓存大小、次数和状态代次。离线实测使用用户指定录音，报告不得把同源裁剪算成独立测试样本。

## 10. 分发、性能和系统环境

### 10.1 分发

main 已有 CAM++ 固定资产清单和桌面构建检查。继续使用固定来源、大小、摘要与许可说明；不要引入 PyTorch、ECAPA 下载按钮或新模型包作为前提。

### 10.2 性能验证

硬约束：单飞评分、缓存和队列有界、音频事件循环不跑模型推理、ACTIVE 不持续做身份评分、关闭后无遗留推理工作者。

报告分别测量：功能关闭、模型冷启动、安静待机、持续旁人讲话、本人激活与回放、ACTIVE＋TTS、反复开关。记录进程树内存增量和峰值、CPU、加载时间、评分 P50/P95/P99、回放积压、音频事件循环延迟及退出资源。

CAM++ 清单权重约 28.3 MB，不代表运行内存；8 秒 PCM 约 250 KiB，不包含元数据和快照。不给未经实测的总内存或端到端延迟承诺。

初始性能目标：常驻模型的单次评分 P95 不超过 200 ms，已激活时新增控制处理 P95 不超过 10 ms。它们是待测目标，普通笔记本未达标时调整调度／实现或收窄支持范围，不能作为既有通过记录。

首次激活延迟必须拆分为有效语音收集、加载、推理、连接准备和回放等待；不能拿推理耗时冒充“说完到回复”延迟。上一轮 TSE 的 250 MB／500 ms 预算不自动套用为本方案已确认门槛。

## 11. 分阶段实施与验收出口

### P0：冻结合同与建立隔离环境

保存本文件，固定 main/#2980 基线、30 秒规则、范围和复用来源。隔离运行状态目录，确认主分支工作树不变。

出口：边界可审阅，参数中已确认与待测项清楚。

### P1：录入和独立评分基础

提取 3+1、音频一致性、EOF 和取消修复；建立不依赖 ASR 的评分接口。复用现有 CAM++ 和工作进程，不迁 pVAD/TSE。先验证录入、旧档案处理和后台评分真正可用。

出口：同一音频合同形成参考并完成评分；取消／模型失败／档案错配不泄漏资源；不需要 Provider 才能评分。

### P2：纯状态机、缓存与单写者回放

实现 WAITING→VERIFYING→REPLAYING→ACTIVE→WAITING；默认 30 秒无语音。用可控时钟和标记音频测试截止、缓存淘汰、重复帧、迟到结果、关闭和部分发送失败。

出口：音频内容和顺序满足合同，待机不上传，激活后不逐句评分，无无限缓存和任务积压。

### P3：两条生产路径与 UI 接线

共同入口组装控制器；停止原逐句声纹过滤器在本模式中的挂载；接通独立 ASR/native。处理 Provider idle timeout、原生会话静音自动结束、重连、hot-swap 和现有 pre-roll 的兼容，增加状态事件与 8 语言文案。

出口：至少一条独立 ASR 和一条原生音频端到端通过；本人激活后的“嗯／好”不因声纹拦截；关闭功能恢复普通语音且不补送旧缓存。

### P4：发行包、性能和环境验证

实测发行资产、工作进程和普通 CPU。完成 30 分钟待机／交互混合运行及反复开关，明确平台和 Provider 实测范围。真实录音初筛使用现有样本；证明身份准确率还需要与参考独立的数据，不用裁剪数量凑样本规模。

出口：实包可运行、资源有界、测试和风险记录可供 review；不把待验证环境写成已支持。

### P5：审查和发布准备

按 main 对比整理小范围提交，说明来源和回归点。提交前 GitNexus detect-changes，核心模块人工 review；报告新增代码覆盖率与相关回归，项目要求的检查通过后准备 PR。生产发布／外部发消息依后续明确授权执行，当前计划不自动发布。

## 12. 必须覆盖的验收用例

| 类别 | 用例与断言 |
|---|---|
| 本人激活 | 长度足够的本人语音触发，缓存开头保留、仅发送一次 |
| 短句 | 待机不因不足证据激活；ACTIVE 下同一短句进入普通链路 |
| 旁人 | 待机旁人语音不应激活；ACTIVE 下接收符合产品规则 |
| 30 秒 | 29.9 秒人声续期；真正超过 30 秒重新验证；旧回放不能续期 |
| 回放顺序 | 验证结束与新帧并发、帧重排、hot-swap、既有 pre-roll 不重复 |
| 故障 | 模型丢失／损坏／NaN／超时、连接失败、结果不明均不伪装成功 |
| 身份退休 | 推理和回放各关键 await 中关闭、取消、换档案、换路由；旧结果无权限 |
| 溢出 | 缓存开头淘汰、队列满、回放追不上均有明确失败，不截断后冒充完整 |
| 静音与回声 | 无人、噪声、猫娘播报回声、用户打断播报，不无限维持激活 |
| 环境与资源 | 冷启动、实包启动、无网已有模型、重复开关、长待机，无遗留进程 |

报告分别统计本人未激活、旁人误激活、证据不足、故障、激活后普通放行。单位至少包含实际独立句和待机会话时长，不只报告单个窗口的高分率。验收先冻结预期与参数，再运行独立数据，不能测试后临时调阈值并宣布通过。

## 13. 改动风险与实施守门

整体按高风险语音入口改造审查。已有 GitNexus 对 #2980 的共同入口显示直接调用方包含实时采音和 hot-swap 回放，但该索引不是 main 新分支的准确调用图；新工作目录已启动单独索引，实际修改每个现有符号前必须在正确基线上重新 impact。

高风险集中在：评分等待阻塞采集、回放和实时输入交错、旧过滤器二次拦截、native idle timeout 提前关麦、模式切换错投旧音频、打包后进程失败。模型分数好不能替代这些链路验证。

修改核心模块后报告改动理由、前后行为、回归和限制；Python 一律通过 uv run；UI 覆盖 Web 与 Electron。分阶段运行必要测试，不以大量 mock 或全量通过数量代替真实发送路径证据。

### 14.1 已实现

- P0：已固定 main `e7594e1333f918135df012694d2378896d13a25e` 基线、#2980 参考点、30 秒规则和不纳入范围的 pVAD／ECAPA／TSE／校准参数包。

- P2：新增与 Core／Provider 解耦的激活控制器、8 秒／256,000 字节有界缓冲、最多一个在途评分加一个候选、单写者回放、发送结果分类和完整 generation fence；实现 PREPARING→WAITING→VERIFYING→REPLAYING→ACTIVE，以及连续 30 秒无本地有效人声后返回 WAITING。1.5／3 秒候选时长只累计有效人声，连续静音或人声间隔达到 0.5 秒即清空候选。
- P3：在统一 16 kHz 麦克风入口接入会话激活，覆盖 native 音频会话与 independent ASR；WAITING／VERIFYING 不把麦克风 PCM 交给 Provider；本人确认后按序回放且每帧只提交一次；ACTIVE 不再运行逐句声纹过滤；关闭、停麦、换路由、换档案和权限变化立即退休旧运行时。采集单调时刻随排队、预处理和 hot-swap 完整保留；启用激活时，旧路由帧不能在 worker、hot-swap 或 QueueFull 重试处重绑到新路由。安装新会话门时会解除旧逐句过滤器，避免双重判定。
- P3 native idle：仅对已分类的 `API_IDLE_TIMEOUT` 延迟回收；下一次本人确认后，在回放前原地重连并重启监听。失败保持回放待重试，结果不明不自动重放；档案或权限代际替换与在途重连通过 Core 会话交换锁串行化，仍属于当前会话的 idle 标记安全迁移到新代际。若用户此时关闭声纹激活，第一帧普通音频也会先完成同一受控重连。
- P3 UI：新增带代次和递增 revision 的 `VOICE_SESSION_ACTIVATION_STATE` 事件；八语言区分等待本人、已激活和不可用；录入页说明已改成用户可理解的激活规则；激活设置模块位于四段录音区下方，并提供默认收起的展开／隐藏按钮。
